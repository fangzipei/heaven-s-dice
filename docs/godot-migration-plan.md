# Godot 迁移评估与计划

日期：2026-11-01

## 结论先行

**不建议现在立刻整体迁移。**

当前产品已经把「核心规则、内容、线上账号、存档、测试」跑通，Web 端还有明显的 UI/动画打磨空间。更稳妥的路径是：

1. 先用 2–4 周把 Web 端完成产品级打磨。
2. 同时做 **Godot 纵切片**：只复刻一场战斗 + 一次商店 + 一个 Boss，验证手感、动画成本和导出目标。
3. 纵切片达到验收标准后，再决定是否投入 6–9 人月做完整迁移。

如果目标是 **Steam / iOS / Android**，Godot 值得做。  
如果核心目标仍是 **浏览器即点即玩、分享链接、快速迭代**，继续 Web 的投入产出比明显更高。

## 1. 当前项目体量

| 项目 | 现状 |
|---|---|
| 游戏代码 | 约 180 个 TypeScript 文件，约 13,600 行 |
| 测试 | 25 个测试文件，约 4,300 行，384 项测试 |
| 核心引擎 | `engine.ts` 约 2,600 行，另有计分/事件/类型约 1,200 行 |
| 内容 | 37 枚骰子、19 只骰桶、43 件物品、25 关、完整 Boss 池 |
| 表现层 | DOM + CSS + Three.js 骰子 + GSAP 动画 |
| 后端 | 独立 HTTP API，账号、历史、未完成对局、排行榜 |
| 美术 | SVG 纸艺 UI、骰面/骰桶/物品/立绘、Three.js 模型 |

这不是一个「一天能搬到 Godot」的小项目。真正的成本不在规则，而在 **表现层重写 + 动画重做 + 跨端适配 + 线上功能对接**。

## 2. 迁移方式选择

### 方案 A：继续 Web，做产品级打磨

**周期：2–4 周**  
**成本：约 ¥3 万–8 万（外包）或 0.5–1 人月**

适合：

- 核心用户来自链接分享、浏览器、轻量试玩
- 需要快速迭代数值和内容
- 不希望维护两套客户端

风险最低，也是当前最推荐的短期方案。

### 方案 B：Godot + GDScript，优先桌面/移动，Web 作为附加

**周期：6–9 人月**  
**成本：约 ¥25 万–60 万（外包）/ ¥50 万–90 万（小团队全包）**

适合：

- 目标包含 Steam、iOS、Android
- 希望统一渲染、输入、音频和打包
- 能接受一次完整重写

Godot Web 导出可用，但包体、首屏、字体和复杂 UI 在移动浏览器上不如现有 Web 稳。**如果 Web 是主战场，不建议用 Godot 替换。**

### 方案 C：Godot + C#

**周期：6–10 人月**  
**成本：略高于方案 B**

优点：

- 强类型，接近现有 TypeScript 的工程习惯
- 引擎逻辑移植更安全
- 适合桌面/移动长期维护

风险：

- **Godot 的 C# Web 导出支持需要按目标版本单独验证**。如果 Web 是硬要求，默认选 GDScript，避免中途发现导出链不可用。
- C# 构建链、热重载、移动端裁剪都比 GDScript 多一层复杂度。

### 推荐

- **Web 必须保留** → 方案 A，Godot 只做纵切片验证。
- **Steam/移动是明确商业目标** → 方案 C，先做纵切片。
- **只想快速跨端、Web 非核心** → 方案 B。

## 3. 推荐路线：先纵切片，再全量

### 阶段 0：准备与冻结（1–2 周）

产出：

- 内容导出为 JSON/CSV：骰子、骰桶、物品、关卡、Boss、商店权重
- 规则文档：计分、重投、浮动分、Boss 特例、魔鬼重来
- 固定随机种子的回放样本
- 当前 Web 端关键界面截图和动效录屏

验收：

- Godot 不依赖手抄内容，能从数据文件生成全部内容表
- 同一随机种子在 Web 和 Godot 得到同一组骰面与同一分数

成本：约 1–2 人周。

### 阶段 1：Godot 纵切片（3–5 周）

范围只做：

- 一关普通战斗
- 一次计分 + 重投 + 全骰
- 一个 Boss 特例
- 一次商店购买
- 一个结算界面

产出：

- 可运行桌面构建
- 可运行移动触屏构建
- 动效基准：摇骰、落骰、选中、计分、Boss 出场

验收：

- 核心战斗操作 60fps
- 动画手感不弱于 Web
- 规则与 Web 回放一致
- 内容数据零手写

成本：约 **3–5 人周 / ¥8 万–15 万**。

### 阶段 2：规则与内容全量移植（4–6 周）

- `scoring.ts` → GDScript/C# 计分器
- `engine.ts` → 状态机、重投、Boss、商店、经济
- 37 枚骰子、19 只骰桶、43 件物品、25 关
- 内容快照测试 + 固定种子回放

验收：

- 同一存档在 Web/Godot 结果一致
- 规则测试覆盖全部 Boss 和物品
- 无「Godot 版偷偷改数值」

成本：约 4–6 人周。

### 阶段 3：战斗 UI 与动画（6–8 周）

这是最大的一块，不能低估。

- 桌面布局、右侧信息栏、手机竖屏/横屏
- 3D 骰子材质、骰面、摇骰/落骰/选中/计分动画
- 纸艺 UI、HUD、Boss 立绘、语音气泡
- 手势仪式、轨迹、烟雾、火焰、金币飘字
- 动效编辑与性能优化

验收：

- 手机 60fps（中端机）
- 桌面 120Hz 不撕裂
- 动效可跳过、可降级
- 无布局跳动

成本：约 6–8 人周。

### 阶段 4：商店、图鉴、账号、后端对接（4–6 周）

- 商店、刷新、替换、礼包、重铸
- 图鉴、教程、规则
- 账号、历史、未完成对局、排行榜
- 存档格式与云同步

验收：

- 现有 API 不需要大改
- 换设备继续对局
- 旧 Web 存档可迁移

成本：约 4–6 人周。

### 阶段 5：音频、打磨、导出、QA（4–6 周）

- 音效、音乐、混音
- 自适应分辨率、安全区、手柄
- Steam/移动/Web 导出
- 崩溃、存档、弱网、购买恢复
- 与 Web 端逐项视觉对照

成本：约 4–6 人周。

## 4. 成本汇总

### 外包/顾问口径

| 范围 | 人周 | 费用区间 |
|---|---:|---:|
| 纵向切片 | 3–5 | ¥8 万–15 万 |
| MVP：单章节 + 基础商店 + 无线上 | 10–14 | ¥25 万–40 万 |
| 功能对齐：完整内容 + 账号 + 商店 | 22–30 | ¥50 万–90 万 |
| 产品级：动画、音频、移动端、QA | 28–38 | ¥70 万–130 万 |

按 ¥25k–45k/人周估算，未含长期运营、美术重绘和商店发行费用。

### 小团队口径

2 人（Godot 开发 + 美术/动效），4–5 个日历月：

- 人力成本约 **¥40 万–80 万**
- 如果还要保留 Web 同步更新，需要额外 0.5–1 人长期维护

### 隐性成本

- 两套客户端意味着双倍回归测试
- 数值改动需要同时验证两端
- 动画资产、字体授权、移动端适配
- Steam/移动发行的账号、隐私、支付和审核
- 线上存档迁移和客服成本

## 5. 技术映射

| 当前 | Godot 方案 |
|---|---|
| TypeScript 纯规则 | GDScript 或 C# 状态机，保持无 UI 依赖 |
| `scoring.ts` | 独立计分器 + 固定种子回放 |
| DOM/CSS HUD | Control 节点 + Theme + 9-slice 纸艺图 |
| Three.js 骰子 | Mesh + 材质 + AnimationPlayer |
| GSAP | Tween / AnimationPlayer |
| SVG 纸艺 | 导入 SVG 或预渲染 PNG/9-slice |
| 本地存档 | JSON 存档 + 版本迁移 |
| 现有 API | 原样复用 HTTP；Godot HTTPRequest |
| Vitest | GUT / GdUnit4 + 回放对照 |
| Web 内容表 | 构建时导出 JSON，Godot 读取同一份数据 |

关键原则：

1. **规则层不碰 UI**。
2. **内容单一来源**：Web 和 Godot 读同一份 JSON，禁止手抄。
3. **回放金标准**：先用 Web 生成 100–500 局固定种子结果，Godot 逐局对齐。
4. **先纵切片再全量**，不要先做「大而全的框架」。

## 6. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 动画重做低估 | 工期翻倍 | 纵切片先做完整一场战斗 |
| 纸艺 UI 在 Godot 中失真 | 品牌感下降 | 9-slice + 预渲染 + 主题化 |
| 移动端性能 | 掉帧、发热 | 限制实时阴影/后处理，提供低画质 |
| C# Web 导出不可用 | 无法交付 Web | 先验证导出链，Web 优先用 GDScript |
| 双端数值漂移 | 玩家投诉 | 共用 JSON + 回放测试 |
| 账号/存档迁移 | 老玩家流失 | 服务端做格式转换，不依赖客户端 |
| 两套客户端维护 | 长期成本 | 明确 Web 与 Godot 的主次 |

---

## 7. 建议的决策门槛

先投入纵切片，只有同时满足以下条件才进入全量：

- 一场战斗的完整操作在桌面和手机都顺畅
- 骰子动效达到或超过 Web 端
- 同种子回放 100 局零差异
- 目标平台导出成功
- 纵切片实际耗时不超过 6 人周
- 团队能接受 6–9 人月的全量周期

如果任一条件不满足，继续 Web 打磨更划算。

## 8. 现在就能做的准备

不需要等 Godot 立项，以下工作对两端都有价值：

1. 把内容表导出为 JSON，作为唯一数据源。
2. 把 `engine.ts` 的随机数入口固定为可注入种子。
3. 建立 200 局固定种子回放金标准。
4. 把 UI 动效拆成可复用的时间轴规范（入场、选中、计分、Boss、商店）。
5. 统一纸艺设计 token：颜色、字体、间距、圆角、阴影、动效时长。
6. 先完成 Web 端 UI 打磨，作为 Godot 的视觉基准。
